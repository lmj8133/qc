Flashing the Ubuntu Image to a QCS8550 EVB

How to write the QTI Ubuntu fullstack image onto an Aida3 RDK socket board over USB, using Qualcomm's EDL recovery protocol. Start to finish, about 20 minutes.

Board
aida3_RDK_SOCKET Rev 1.0
SoC
QCS8550 (kalama)
Image
V00.00.03
Host OS
Ubuntu 24.04 x86_64
Flash time
~12 min
Last verified
2026-09-14

This erases the board completely

Flashing rewrites the entire UFS storage — bootloader, TrustZone, boot, dtbo and roughly 21 GB of system partitions. Everything currently on the device is destroyed, with no undo.

Once flashing starts, do not unplug the USB cable, power-cycle the board, or let the host PC sleep. An interruption while the bootloader partitions are being written can leave the board unable to boot on its own. That state is recoverable — see Recovery — but only if you can force EDL mode in hardware.

01

How this works

Worth understanding before you run anything, because it explains why the procedure is safe to retry and hard to permanently break.

The board is flashed through EDL (Emergency Download Mode), a protocol built into the SoC's Primary Boot Loader — mask ROM inside the chip itself. Because EDL lives in ROM, nothing you write to storage can erase or corrupt it. That is the entire reason a failed flash is recoverable.

The host tool is qdl, which speaks EDL over USB. It first uploads a small programmer binary (xbl_s_devprg_ns.melf) into the SoC's memory, then streams every partition image described by the rawprogram*.xml and patch*.xml files. No working bootloader is needed on the board.

You can tell the board's state from its USB ID alone:

USB IDModeWhat it means
05c6:901d Mission Board booted normally into its OS. adb works. The script will switch it to EDL for you.
05c6:9008 EDL / QDL Ready to be flashed right now. This is also what a non-booting board looks like, which is why a failed flash is fixable.
nothing — No USB connection, no power, or the board needs a hardware EDL trigger.
02

One-time host setup

Run these once per host PC. Skip if the machine has flashed a board before.

Install the tools

# 7-Zip to unpack the image archive, adb to switch the board into EDL
sudo apt update
sudo apt install -y p7zip-full android-tools-adb

Allow USB access without root

qdl needs raw USB access. Without a udev rule you would have to run the whole flash as root, which is worth avoiding. 

sudo tee /etc/udev/rules.d/51-qualcomm-edl.rules <<'EOF'
SUBSYSTEM=="usb", ATTR{idVendor}=="05c6", MODE="0660", GROUP="plugdev"
EOF

sudo udevadm control --reload-rules
sudo udevadm trigger

Then confirm your account is in the plugdev group:

id -nG | tr ' ' '\n' | grep plugdev
If that prints nothing: run sudo usermod -aG plugdev $USER, then log out and back in. Group changes do not apply to an existing session.
03

Confirm the board variant

The flash script takes one argument — rdk or grizzly. This selects the CDT (Configuration Data Table), a 24-byte block read by the first-stage bootloader to identify which board it is running on. Get it wrong and the board may configure DDR or peripherals incorrectly.

rdk our boards

4344 5400 … 0200 0300

Board ID 0x03. Use this for aida3_RDK_SOCKET.

grizzly

4344 5400 … 0200 0400

Board ID 0x04. A different carrier board — do not use unless told to.

The two files are identical except for that single byte. If you are ever unsure and the board still boots, read the CDT it is already running and compare: 

# On a board running the Ubuntu image
adb shell "dd if=/dev/disk/by-partlabel/cdt bs=1 count=24 2>/dev/null | xxd"

# Compare against the file you intend to flash
xxd aim300_rdk.bin
Path differs by image. The Ubuntu image exposes partitions at /dev/disk/by-partlabel/. The older Android-style image used /dev/block/by-name/. Using the wrong path returns empty output, which looks alarming but means nothing is wrong.
04

Flashing procedure

  1. Unpack the image archive

    Roughly 3.5 GB compressed, expanding to about 21 GB. Make sure you have at least 30 GB free.

    cd ~/work/qcs8550
7z x qcs8550_ubuntu_flatten_V00.00.03.7z
cd flatten_image

    You should now see qdl_flash.sh, a QDL/ directory, the rawprogram*.xml files and several hundred system_*.img chunks.

  2. Connect the board and confirm the host sees it

    Plug the EVB into the host over USB and power it on.

    lsusb | grep -i qualcomm

    Expect either 05c6:901d (booted) or 05c6:9008 (already in EDL). Either is fine. If nothing appears, stop and fix the connection — do not proceed.

  3. Check the XML is clean

    The script temporarily writes the CDT filename into rawprogram3.xml and restores it afterwards. If a previous run was interrupted, a stale value can be left behind.

    grep 'label="cdt"' rawprogram3.xml | grep -o 'filename="[^"]*"'

    This must print filename="". If it shows a .bin filename, clear it before continuing.

  4. Run the flash

    One command. Pass your board variant from step 03.

    ./qdl_flash.sh rdk

    The script switches the board into EDL if needed, uploads the programmer, then writes every partition. Logging the run is recommended:

    ./qdl_flash.sh rdk 2>&1 | tee flash.log

  5. Wait — and leave it alone

    Expect around 12 minutes at roughly 30 MB/s. Progress appears as a long series of flashed "system" successfully lines.

    Do not touch the cable, the board, or the host. When it finishes you will see [Step 5] Flashing completed! and the board reboots itself into the new image within about 20 seconds.

05

Verify the result

Work through these after the board comes back up. Ticks are saved in your browser only. 

# Board is back on USB in Mission mode
lsusb | grep -i qualcomm

# adb reports the Ubuntu product string
adb devices -l

# Confirm the OS and kernel
adb shell "cat /etc/os-release | head -3; uname -a"

Kernel hash matters. The g576728c775df suffix must match the Metadata Revision in the application SDK's version-aarch64-oe-linux file. When they match, binaries cross-compiled with that SDK link against exactly the libraries present on the device.
06

Troubleshooting

SymptomCause and fix
No Qualcomm device is detected Board not powered, wrong USB port, or a charge-only cable. Confirm with lsusb before rerunning.
Permission denied from qdl udev rule missing or group not applied. Re-check section 02; remember group changes need a fresh login.
Stuck at waiting for programmer… The board entered EDL but did not accept the programmer. Power-cycle the board, let it reach EDL again, and rerun.
adb wait-for-device never returns Board is in Mission mode but adb cannot see it. Check adb devices; if empty, the udev rule for 05c6 is missing.
Flash aborted partway Board is almost certainly still in EDL (05c6:9008). Clear the stale CDT entry from rawprogram3.xml, then rerun the same command.
Board does not re-enumerate after flashing Wait a full minute first — the first boot after a flash is slow. Then power-cycle. If still absent, go to Recovery.
CDT read returns nothing Wrong partition path for the running image. Ubuntu uses /dev/disk/by-partlabel/, not /dev/block/by-name/. Not a fault.
07

Recovery

A board that will not boot is not a dead board. Work down this ladder.

StateAction
Boots normally Nothing special — just rerun ./qdl_flash.sh rdk.
Will not boot, but shows 05c6:9008 Rerun the same command. The script detects EDL directly and skips the adb step entirely. This is the normal outcome of a bad flash.
Nothing on USB at all Force EDL in hardware using the board's EDL button, jumper, or test points, then flash as normal.

Find the EDL trigger before you need it

Locate your board's hardware EDL button or jumper and note it somewhere findable — ideally before your first flash. It is the difference between a five-minute recovery and a board sitting on a shelf. Check the aida3_RDK_SOCKET schematic or ask the hardware team.

Flashing from Windows instead

If you have no Linux host, the same image set flashes from Windows. It needs Qualcomm's USB driver installed so the board appears as QCOM USB QDLoader 9008. 

aim_image_loader.bat rdk auto

auto detects the 9008 COM port; pass a port number instead if detection fails. This path uses rawprogram3_rdk.xml directly rather than patching the XML, so the step-03 cleanliness check does not apply.

After flashing: running your own binaries

Applications built with the QCS8550 application SDK can be pushed straight to the board: 

# On the host, in an SDK-configured shell
. ~/work/qcs8550/sdk/environment-setup-aarch64-oe-linux
$CC hello.c -o hello

adb push hello /data/
adb shell "chmod +x /data/hello && /data/hello"
